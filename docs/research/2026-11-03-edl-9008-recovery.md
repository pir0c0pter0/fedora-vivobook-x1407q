# X1407QA EDL 9008 recovery status (2026-11-03)

This note consolidates the USB/firmware diagnosis performed after the ASUS
Vivobook 14 X1407QA stopped booting. It supersedes the earlier assumption that
the machine was merely failing to enumerate over USB. The complete local
evidence bundle remains outside Git in `../diagnostico-x1407qa`; this document
keeps the repository-level facts, safety boundary, and next recovery steps.

For a clean-context continuation in Portuguese, start with
[`2026-11-03-edl-9008-handoff.md`](2026-11-03-edl-9008-handoff.md).

## Current result

The notebook is alive in the Qualcomm Primary Boot Loader and communicates over
USB in Emergency Download mode:

```text
USB VID:PID:          05c6:9008
Protocol:             Sahara v3
HW ID:                002ad0e100290000
MSM ID:               002ad0e1
OEM ID:               0029
Model ID:             0000
OEM PK hash:          fd5f133f0db1b89904e66a74d242fb5e
                      dc5760b35d24793ffc7cc077b73fdcadd
                      70f59436a9dd53f8004c37e3340e1f7
```

The unit-specific serial is deliberately omitted from the repository. A live
`qdl v2.9 chipinfo --debug` query repeated at 15:47 local time returned the same
Sahara version, HW ID, and OEM PK hash after resetting only the USB endpoint.
No programmer, firmware image, XML, erase, patch, or provisioning command was
sent.

This proves that the cable, host port, USB PHY, PBL, and Sahara command path are
working. It does **not** prove that the boot flash, RAM, UEFI, or BIOS capsule is
healthy, and it does not identify the original component that caused the sudden
power-off.

## Observed hardware path

The motherboard is marked `X1407QA-PMV-DY`, part
`6050A3656905-MB-A01`. The two-position `SW2100` service switch changes boot
behavior, but its electrical function is not documented:

| SW2100 | USB-C data port used in the successful tests | Result |
|---|---|---|
| 1 ON / 2 OFF | The USB-C port that originally held the charger | Stable `05c6:9008`, Sahara v3 |
| 1 ON / 2 ON | Same port | Stable `05c6:9008`, Sahara v3 |
| 1 OFF / 2 OFF | Same port | No EDL enumeration during the observed window; normal boot still failed |
| 1 OFF / 2 ON | Same port | No USB event during a 30-second kernel/udev observation window |

The association between switch 1 and EDL is observational, not a schematic-level
identification. Disconnect all power before changing the switch positions.

Two 4 KiB PBL debug records were read, one with `1 ON / 2 OFF` and one with both
switches ON. Both stop at the same stage:

```text
APBL start
APBL Boot Media Detect Start
APBL Boot Media Detect End
APBL SHELF Load+Auth Start
```

Neither record contains a completion marker or explicit error after
`SHELF Load+Auth Start`. The close timestamps in both switch configurations do
not distinguish corrupted boot media from authentication, memory, or another
early-boot failure.

Sahara memory-debug mode was requested without a programmer after clean USB
reconnections. Both switch configurations returned raw status `0x1b` and
exposed no memory table. The older client used during collection labels it
`Invalid mode switch`; current `linux-msm/qdl` labels the same value `memory
debug not supported`. The raw status and failed request are authoritative. The
only target-derived binaries are small 4 KiB PBL debug records; there is no full
BIOS, flash, UFS, or partition dump.

### Follow-up with the SSD installed

The official `X1407QA.314` capsule was placed on a verified single-partition
FAT32 USB drive and tested with both SW2100 switches OFF. Automatic ASUS BIOS
recovery did not start.

The internal NVMe SSD was then reinstalled and the notebook was started with
both switches ON. It returned to `05c6:9008`. A fresh 4 KiB PBL debug read still
ended at `APBL SHELF Load+Auth Start`; only 9–10 timestamp bytes differed from
the earlier captures. Reinstalling the SSD therefore did not move the observed
failure boundary. The final `1 OFF / 2 ON` switch combination produced no USB
event; returning both switches to ON restored stable `05c6:9008` enumeration.

## Official firmware checked

ASUS package `SOCPackage_forWebSite_Qualcomm_Z_V1.314.8800.0_50054.exe` was
downloaded and inspected offline:

| Item | Value |
|---|---|
| ASUS package SHA-256 | `caf0cbd096a4eca8788f4a910a4d34ca1c2174b9e0875d0feaada7fa45356f17` |
| BIOS payload filename | `X1407QA.314` |
| BIOS payload SHA-256 | `afcdc9a4b6cc73813768eacbccc46918bae03ba4c4534717083a147d6d793dc3` |
| Payload type | UEFI FMP capsule, 15,294,564 bytes |
| Firmware version | `10.1.2.314` |
| Firmware ID | `83542aec-9b0c-5b26-9431-41f0195b9059` |

The package installs the capsule through the Windows UEFI firmware resource
and `pnputil`; it does not contain a demonstrated X1407QA Firehose programmer,
`rawprogram*.xml`, or `patch*.xml`. The capsule is not a raw flash dump and must
not be passed to QDL as a programmer.

The OEM PK hash returned by Sahara exactly matches the SHA-384 of the
`Generated ASUS Root CA` certificate embedded in the official capsule. This
ties the live device identity to the ASUS firmware chain, but it does not turn
the capsule into an EDL loader.

## Loader search and exclusions

Searches covered the exact model, motherboard markings, full HW ID, full OEM PK
hash, bkerler/Loaders, Temblast, GitHub code, the ASUS BIOS 306 and 314 packages,
the ASUS WinRE package, and public Qualcomm X1E80100 IQ-X EVK packages.

No public loader matching both this HW ID and ASUS OEM PK hash was found. The
search was repeated on 2026-11-03; GitHub code and the current Temblast catalog
still had no exact match.

A deeper offline extraction of all 24 capsule components found normal Qualcomm
XBL, UFS, SPI-NOR, TrustZone, and `XBLRamDump` images. The latter is an AArch64
ELF built for `SocHamoaWP`, contains Sahara dump support, and includes a modern
signature segment with the ASUS root certificate. It is nevertheless a RAM-dump
stage from the capsule/SHELF update flow, not a demonstrated Firehose programmer.
Other signed inner components use Qualcomm PK hash `467f3020c4cc788d...`, not
the ASUS device hash `fd5f133f0db1b899...`. No capsule component is therefore a
validated standalone Sahara programmer.

### Controlled `XBLRamDump` format check

After offline inspection, the exact extracted `XBLRamDump` (SHA-256
`f327e4c7d44969c3b76b4a6fea4bc57e64f49490ce5ac435e427c2271056cf49`) was
offered once to Sahara with execution deliberately disabled: the client did not
send `SAHARA_DONE_REQ`, and no Firehose command or storage operation followed.
PBL requested image ID 13 and accepted the 64-bit transfer framing, then
returned `END_TRANSFER` status `0x29`. Current `linux-msm/qdl` decodes this
status as `invalid ELF image format received`. The image was rejected before
execution; it cannot be used directly as this machine's Sahara programmer.

The USB endpoint was reset after the check, and a fresh `qdl chipinfo --debug`
query returned the same Sahara identity and OEM PK hash. Nothing was written to
the SSD or boot flash. Do not repeat this test with another capsule component:
the exact rejected status already closes this route, while an accepted image
could execute immediately in an ordinary client.

The Qualcomm IQ-X 1.0, 1.2, 1.3, and 1.4 EVK packages contain
`xbl_s_devprg_ns.melf`, but their certificate roots do not match the ASUS OEM PK
hash. They target a different board and remain unsafe for this notebook. Do not
send them experimentally, and do not use their erase/program XML files.

## Recovery order

1. **Vendor non-EDL recovery was attempted without success.** A separate FAT32
   drive containing the verified official `X1407QA.314` file at its root did
   not start automatic recovery with both SW2100 switches OFF. Do not repeat
   this power cycle indefinitely.
2. **If UEFI recovery never starts, obtain an ASUS-signed X1407QA service
   programmer.** Match the complete HW ID and OEM PK hash, then validate its
   provenance, certificate chain, target memory type, and board compatibility
   offline.
3. **The first Firehose operations must be read-only.** Query programmer and
   storage identity/geometry without `rawprogram`, `patch`, erase, provision, or
   reset XMLs. Read the complete device twice to separate files, hash both, and
   require byte-for-byte equality before analysing or changing anything.
4. **Preserve unit-specific data.** Compare structures and regions against the
   official capsule only after a verified complete backup. A capsule version
   difference is not by itself proof of corruption.
5. **If no matching programmer is available, stop at ASUS board-level service.**
   Trying a loader for the same Snapdragon family but another OEM/board is not a
   recovery method.

The FAT32 capsule attempt and the non-executing `XBLRamDump` format check have
both failed. No further low-risk USB recovery action is known without a genuine
ASUS service programmer. The PBL log does not show completion of the
authenticated load stage, which supports but does not prove that service-level
access is now required.

## Safe reproduction

Read-only identity query with the official `linux-msm/qdl` v2.9 binary:

```bash
sudo qdl chipinfo --debug
```

If QDL reports `unexpected packet 0x4 while waiting for HELLO`, the current
Sahara session is residual. Physically reconnect the notebook's data cable or
reset only the exact `05c6:9008` USB device, confirm its product string again,
and repeat once. Bus/device numbers change after reconnection and must never be
hard-coded from this report.

Do not run QDL with a candidate file merely to see whether it authenticates.
Loading an unverified programmer changes the device execution state and is not
equivalent to `chipinfo`.
